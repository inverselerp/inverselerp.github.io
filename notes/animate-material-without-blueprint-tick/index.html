Animate a material without Blueprint Tick

Send a start time once. Let the material handle the progression of a reveal, fade, or glow.

A dissolve or glow often starts with a Blueprint Timeline: update a float, write it into a material instance, repeat until the animation finishes.

For a simple time-based visual, there is another option. Tell the material when the effect started, then let it calculate how far along it is. Blueprint handles the event. The material handles the progression.

This removes the need for a Blueprint Tick or Timeline to keep writing the animation value. It does not make the shader free or stop it evaluating each rendered frame.

The idea in one line

float progress = saturate((Time - StartTime) / max(Duration, 0.001));

Subtract the start timestamp from the current time to get elapsed time. Divide by the duration to normalize it. Clamp the result to the range [0, 1].

For a one-second transition:

Time since trigger Progress
0.00 seconds 0.00
0.25 seconds 0.25
0.50 seconds 0.50
1.00 seconds 1.00
2.00 seconds 1.00

Nothing needs to keep pushing those intermediate values from Blueprint.

Build the material

Start with a simple Surface / Unlit material on a test mesh. Use a color reveal first; a complicated dissolve can hide problems with the timing.

Add three scalar parameters:

Parameter Default Purpose
StartTime 0 Timestamp written when the effect is triggered.
Duration 1 Transition length in seconds.
Enabled 0 Keeps the material in its starting state before the first trigger.

Then build this chain with ordinary material nodes:

Time ────────── Subtract ── Divide ── Saturate ── Multiply ── Progress
StartTime ──────┘             │                     │
Duration ── Max(0.001) ────────┘                  Enabled

Use Progress as the alpha of a Lerp between a dark color and a bright color, and connect the result to Emissive Color. Set the Time node’s Ignore Pause option off and leave Period disabled for this first example.

Enabled is a regular scalar, not a Static Switch. With its default of zero, the output stays at the start of the reveal even if the level has been running for a while.

The equivalent arithmetic is:

// Conceptual HLSL for the node graph, not a complete standalone shader.
float safeDuration = max(Duration, 0.001);
float progress = saturate((Time - StartTime) / safeDuration);
progress *= saturate(Enabled);
float3 color = lerp(StartColor, EndColor, progress);

Trigger it from Blueprint

On setup, use Create Dynamic Material Instance on the mesh component and keep the returned reference. Create it once, rather than allocating a new instance each time the effect plays.

When an event should start the reveal:

Trigger event
  → Set Scalar Parameter Value: StartTime = Get Game Time in Seconds
  → Set Scalar Parameter Value: Enabled = 1

Set Duration during setup, or on the trigger if it needs to vary.

After that, leave the material alone. The Time node continues advancing and the material derives its own progression. Subsequent triggers can restart the effect by writing a new StartTime.

Parameter names must match exactly between the material and Blueprint. A naming mismatch can look like a timing problem when the timestamp simply never arrived.

Match the clocks

Time - StartTime only makes sense if both values use the same clock.

For the normal gameplay case, start with Get Game Time in Seconds in Blueprint and material Time with Ignore Pause disabled. Verify the pairing in the actual play mode and engine version you intend to use.

  • Do not subtract an actor’s age from a world-time clock.
  • Do not mix real time with game time if pause or time dilation matters.
  • Leave Time’s Period off: a wrapping clock minus an unwrapped timestamp eventually produces the wrong elapsed time.
  • Per-actor custom time dilation does not automatically give a shared material clock that actor’s timing behavior.

If the effect must continue through pause, choose a matching real-time setup deliberately and test both sides. Toggling Ignore Pause alone is not enough to establish that the clocks agree.

Reuse the progression

Once Progress is correct, it can drive more than a color:

  • Fade in: use Progress.
  • Fade out: use 1 - Progress.
  • Ease the transition: use Progress * Progress * (3 - 2 * Progress).
  • Dissolve: compare a noise mask against a threshold driven by Progress.
  • Glow pulse: shape the value so it rises and falls during the interval.

Rewriting the start timestamp restarts the curve at zero. If it was already halfway through, that restart can snap. A continuous retargetable tween needs additional state, such as the starting value; this simple recipe does not provide that automatically.

What this does not replace

Use this pattern when the material only needs to answer, “What should this look like at this time?”

It does not emit a Blueprint completion event, update collision, or manage gameplay state. If gameplay needs to know when the effect ends, use an appropriate timer or other gameplay logic with compatible timing.

The material still has rendering cost. Dynamic material instances also have CPU, memory, and batching implications. Removing repeated Blueprint parameter writes is the specific change here—not a promise that every effect will become faster.

Verify it in a small scene

Before turning this into a reusable function:

  1. Wait several seconds after Begin Play, then trigger. The reveal should still start at zero.
  2. Test durations of 0.25, 1, and 3 seconds.
  3. Trigger twice, including once mid-transition. Confirm the intended restart behavior.
  4. Pause and resume, then test global time dilation.
  5. Trigger two actors at different times. Confirm their material instances are independent.
  6. Check zero and negative duration inputs; this example clamps them to a small positive duration.

Validation status: the equations have automated arithmetic checks, but this exact setup has not yet been reproduced or profiled in Unreal. An in-engine capture and a recorded test version are still pending.
